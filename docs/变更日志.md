#### ⚠️ 重大环境问题与解决：Gradle 测试 worker 无法启动

**现象**：`gradle testDebugUnitTest` 稳定失败，报
```
ClassNotFoundException: worker.org.gradle.process.internal.worker.GradleWorkerMain
Could not write standard input to Gradle Test Executor
java.io.IOException: 管道正在被关闭
```
而 `gradle assembleDebug` 却完全正常。

**排查过程**（逐步排除）：
1. 怀疑脏守护进程 → `gradle --stop` 后重跑，**仍失败**，排除。
2. 怀疑沙箱禁止命名管道 → 用完整权限重跑，**仍失败**，排除。
3. 一度误判为 aapt2 的中文路径报错，但经 Java 侧探针验证：`android.jar` 真实存在、`File.exists()` 为 true、目录列举正常 —— 证明 **Java 内部路径字符串是正确的**，日志里的 `����` 只是控制台编码显示问题。aapt2 那行是 **W 级警告**，aapt2 会自行降级，不是失败原因。
4. 定位真因：**我在 `org.gradle.jvmargs` 里设了 `-Dfile.encoding=UTF-8`**。Java 在 Windows 上构造子进程命令行时使用平台字符集，把守护进程的 `file.encoding` 改成 UTF-8 后，传给 Gradle 测试 worker 的 **classpath 编码错位**（classpath 里所有 jar 路径都含中文 `自律app`），子 JVM 因此找不到 `GradleWorkerMain`。

**修复**：`gradle.properties` 中改为
```properties
org.gradle.jvmargs=-Xmx2048m -Djdk.lang.Process.allowAmbiguousCommands=false
```
去掉 `-Dfile.encoding=UTF-8`，并强制 Java 走安全引号路径。**修复后测试任务立即正常。**

> **教训**：中文路径下不要给 Gradle 守护进程设 `file.encoding`，也不要再设 `android.overridePathCheck` 之外的花招。这条已写入 `gradle.properties` 的注释。

#### APK 验收测试升级为「按里程碑精确匹配权限」

M2 引入了 `androidx.work`（为 M3 保活任务准备），WorkManager 合并了 4 条系统权限，导致 M1 时代"不应有任何权限"的断言失效。

**没有放宽断言**，而是改成更强的形式：为每个里程碑定义**精确的预期权限集合**，断言"不多不少"。这样任何意外引入的权限都会被立刻发现 —— 到 M4/M5 加入无障碍、悬浮窗、定位时，这是防止"悄悄多要权限"的主要防线。

## v1.0.1 · 真机反馈修复

用户在真机上装完后报告两个问题。**两个都是真 bug，且性质不同。**

### bug 1：无法添加习惯，保存后今天界面无显示

**根因（已定位并证实）**：`TodayViewModel.refresh()` 只在 `init { }` 里调用一次。
从「新建习惯」页返回时，`today` 这个导航栈条目仍然存活，
它的 ViewModel 被保留 —— **`init` 不会再执行**，所以列表永远停在旧状态。

数据层没有问题。我用测试证实了这一点：直接调 `HabitRepository.save()` 再查
`todayList()` 是能查到新习惯的，问题纯粹在 UI 刷新时机。

**修复方式不是"补一次手动刷新"，而是从结构上消灭这个 bug 类别**：

把今日列表改为 **Flow 观察**，同时观察两张表：

```kotlin
habitRepo.observeActiveHabits()
    .combine(habitRepo.observeDailyCheckInCounts()) { habits, _ -> habits }
```

- 观察 `habits` → 新增/编辑/归档习惯自动刷新
- 观察 `check_ins` → 勾选打卡后 `checkedToday` 自动更新

> 只观察 `habits` 是不够的：打卡写的是 `check_ins` 表，
> `observeActive()` 不会因为它的变化而重新发射。

这样"插库即刷新"，再也不会因为忘记刷新而出现同类问题。

## v1.0.2 · 锁机失效修复 + 滚轮时间选择器

### bug：锁机时其他应用仍能正常打开（核心功能失效）

**根因是我写的一个致命设计错误**，在 `LockAccessibilityService.handleWindowEvent`：

```kotlin
val windowType = windowTypeOf(event)
if (windowType == null) { hideOverlay(); return }   // ← 判定不出来 = 永不拦截
```

`windowTypeOf` 依赖 `AccessibilityService.getWindows()` + `event.windowId` 匹配，而这个组合**在很多 ROM 上必然失败**：

| 失败原因 | 说明 |
| --- | --- |
| `getWindows()` 返回空 | 部分 ROM 即使声明了 `flagRetrieveInteractiveWindows` 也不给列表 |
| `windowId` 对不上 | `TYPE_WINDOWS_CHANGED` 事件的 windowId 常常不匹配任何现存窗口（事件先于窗口列表更新） |

于是 `windowType` 几乎总是 null → 每次都走"不拦"分支 → **整个拦截永久失效**。

**修复**：把语义改成"**只有确实判定出是非应用窗口才让路**"（`InterceptDecider.shouldYieldToWindow`）。
判定不出来时继续走包名判定，安全性由另外两道独立保险承担：
`CRITICAL_SYSTEM_PACKAGES` 精确匹配 + 白名单里的桌面/输入法。

**同时修掉的第二个错误**：`refreshState()` 是异步的（`scope.launch`），但紧接着就同步读 `cachedLocked`，拿到的必然是**上一次的旧值**。现在拦截判定直接用当次事件取到的新鲜状态，缓存只留给遮挡层文案。

### 修复过程中发现并堵住的一个回归

改完让路策略后我意识到：桌面/输入法的包名各厂商不同（`com.miui.home` / `com.huawei.android.launcher`），**进不了兜底清单**；而内置白名单原先只在用户访问「白名单」页时才写库。

于是全新安装、没进过白名单页时，按 Home 键 → 桌面成为前台 → 不在白名单 → **遮挡层盖住桌面，点「返回桌面」又触发一次 → 用户被永久困死**。

**修复**：运行时探测结果**无条件并入**生效白名单（`InterceptDecider.effectiveAllowList`），与数据库状态无关。

### 时间选择改为滚轮式

## v1.0.3 · 锁机改主机制（踢回桌面）+ 通知仅锁机时显示

### 锁机仍不生效：找到第二个真凶

v1.0.2 修掉了"未知窗口类型就不拦"，但用户反馈仍拦不住。复查后找到**另一个独立缺陷**：

`OverlayController.show()` 用 `WindowManager.addView` 添加遮挡层，**这个动作本身会触发 `TYPE_WINDOWS_CHANGED`，而该事件的包名正是本应用**。事件照常走判定 → `decide()` 因"自己永远放行"返回 `Allow` → 紧接着 `clearOverlay()` → **遮挡层刚显示就被自己关掉**。用户只看到一闪，甚至看不到。

修复：本应用的 `TYPE_WINDOWS_CHANGED` 一律忽略（那是遮挡层自身的窗口变化）；而 `TYPE_WINDOW_STATE_CHANGED` 仍要处理（那是用户真的打开了打卡页）。

### 按用户要求更换主拦截机制：遮挡层 → 「踢回桌面」

遮挡层的可见性依赖浮窗权限 + 窗口层级 + 自身窗口事件干扰，环节多、失败面大（已经出过一次自我关闭的事故）。改为：

| | 旧主机制 | 新主机制 |
| --- | --- | --- |
| 动作 | 盖一层全屏遮挡层 | `performGlobalAction(GLOBAL_ACTION_HOME)` |
| 依赖 | 无障碍 + 悬浮窗权限 + 窗口层级 | **仅无障碍服务** |
| 效果 | 挡在应用前面 | 应用一进前台就被推出，反复打开反复推出 |

`GLOBAL_ACTION_HOME` 只需要无障碍服务本身可用 —— 那是无论如何都必须具备的条件，路径最短。遮挡层**退化为兜底**：只有踢不回去时才显示。

同时修正一个随改动引入的隐患：`Toast.show()` 必须在有 Looper 的线程调用，而判定跑在 `Dispatchers.Default` 上，直接调用会抛
`Can't create handler inside thread that has not called Looper.prepare()`。已改为主线程 `Handler` 投递。

### 新增「拦截自检」页（设置 → 拦截自检）

用户两次反馈"拦不住"，而我无法在真机上调试。拦截依赖四个彼此独立的环节，任一断掉现象都一样，从现象无法区分。因此让 App 自己记录每一环：

```
① 无障碍服务      已连接 / 未连接
② 收到的窗口事件   次数 + 最近包名与时刻（0 次 = 服务连着但事件没来）
③ 最近判定        例如「放行：当前阶段是 IDLE，不是锁机态」
④ 执行拦截        次数 + 最近被拦包名
参考 · 让路 / 锁机判定 / 白名单 / 悬浮窗权限
```

顶部直接给出**结论**，例如「断在第②环：服务已连接但收不到窗口事件，请重新关闭再开启一次无障碍服务」。这样用户不需要 adb 就能告诉我是哪一环断了。

### 通知只在锁机时显示

用户要求：非锁机时间不显示任何通知。改动：

- 阶段为 `LOCKED` / `WARN` → 进入前台并显示通知
- 其余阶段 → `stopForeground(STOP_FOREGROUND_REMOVE)` + `stopSelf()`，**通知彻底消失**
- 微信使用时长秒表也加了锁机门禁，非锁机时间不再触发

> 取舍说明：空闲时退出前台意味着进程可能被系统回收。这不影响锁机 ——
> 到点触发靠精确闹钟（AlarmManager 能在进程被杀后重新拉起应用），
> 而真正的执行者是无障碍服务，与前台服务无关。

### bug：无障碍权限已开启，但权限检查页不显示打钩

**根因**：`PermissionChecker.accessibilityEnabled()` 用**硬编码字符串精确比对**：

```kotlin
val expected = "${context.packageName}/${context.packageName}.service.LockAccessibilityService"
enabled.split(':').any { it.equals(expected, ignoreCase = true) }
```

而 `Settings.Secure.ENABLED_ACCESSIBILITY_SERVICES` 里存的是 `ComponentName` 的扁平化结果，**格式并不唯一**：

| 形式 | 示例 |
| --- | --- |
| 长格式 `flattenToString` | `com.zilv.app/com.zilv.app.service.LockAccessibilityService` |
| 短格式 `flattenToShortString` | `com.zilv.app/.service.LockAccessibilityService` |

## v1.0.5 · 通知彻底只在锁机时出现

用户补充要求：**非锁机时间不显示通知，打卡成功后也不显示。**

v1.0.3 已经做过一次"只在 LOCKED/WARN 显示"，但仍有 **三条路径在漏**：

### 漏点 1：`ACTION_FOREGROUND_CHANGED` 也会进入前台（主要原因）

`onStartCommand` 开头**无条件**调用 `startForegroundCompat`，然后才按 action 分支。
而 `ACTION_FOREGROUND_CHANGED` 是由无障碍服务在**每次切换应用**时发出的 ——
于是非锁机时间每次切应用都会先弹一条"正在检查"再收起来，表现为**反复闪通知**。

修复：把刷新类 action 提到最前面处理，**绝不进入前台**。
这两个 action 走的是 `startService`（只有服务已在运行时才送得到），
本身就不需要、也不应该重新 `startForeground`。

### 漏点 2：`AlarmReceiver` 每次闹钟都无条件拉起服务

窗口结束的闹钟也会触发一次启动 → 弹一下通知。
修复：先查状态，只有 `LOCKED` / `WARN` 才 `start()`，否则改为 `notifyStateChanged()`
（仅让已在运行的服务重算并收起通知）。

`MainActivity.onStart` 同样处理 —— 原先只要有启用规则就启动服务，所以**每次打开 App 都会闪一条通知**。

### 漏点 3：打卡成功后没有任何东西触发重算

打卡写库后，锁机状态从 `LOCKED` 变成 `UNLOCKED`，但前台服务不知道 ——
通知栏会一直挂着"锁机中"，直到下一个闹钟或 15 分钟后的自检才发现。

修复：新增 `ACTION_STATE_CHANGED` 与 `LockForegroundService.notifyStateChanged()`；
`CheckInViewModel` 在**打卡成功**与**异常解锁**后各调用一次，立即重算并收起通知。

### 顺带做的可测试性改造

`CheckInViewModel` 原先直接依赖 `LocationProvider`（需要 Android Context），因此**从来没有单元测试**。
抽出 `LocationSource` 接口后，打卡流程变得可测 —— 而"通知是否在打卡后收起"正是需要自动验证的行为。

### 新增测试 8 个（`CheckInViewModelTest`，该文件原先不存在）

| --- | --- |
| **打卡成功后触发锁机状态回调** | 通知不收起这个 bug 的直接回归测试 |

## v2.2 · 打卡即解锁：打卡条件与解锁方法统一

### 术语澄清（用户亲自纠正）

- **打卡** = 一次完成、**连续天数 +1**
- **打卡条件** = 习惯级的两个取值：**指定地点** / **无**

### 1. 室内无法检测地点

室内 GPS 拿不到定位，导致「指定地点」的习惯在室内完全打不了卡。

解法：把打卡条件设为**「无」**——在室内点一下就能打卡。

- 「无」→ "什么时候都能打卡（室内也能用）"
- 「指定地点」→ "必须到打卡点才能打卡（室内可能定位不到）"

（永久把这条习惯的打卡条件改成「无」），而不是让用户卡在"出错了"上。

### 2 & 3. 解锁方法 = 打卡方法，打卡即解锁

**`UnlockMode`（仅定时解锁 / 需地点打卡）这个用户选择取消**。

它原本的含义是"打卡没用，只能等时间到"——与"解锁方法为打卡"直接冲突。
现在解锁统一为两条路：

```
解锁 = 习惯打卡（按该习惯的打卡条件）  或  锁机时长走完
```

- `WindowScheduler.isValidCheckIn` 删掉了 `unlockMode.checkInUnlocks` 那道门，**任何打卡都算**
- `checkInPhaseOf` 删掉 `TIME_ONLY` 特判
- **「打卡条件 = 无」的习惯也允许开锁机**；锁机时点一下打卡即解锁
  （用户确认接受这种弱约束，符合本项目"只做表面锁机"的一贯取向）
- `LockRule` 的 `spotId` 退出校验；打卡点归**习惯的打卡条件**管
- `unlockMode` 列与 `UnlockMode` 枚举保留（旧数据解码要用），但不再影响任何行为

### 关键数据打通：习惯打卡也能解锁

`LockRuleRepository.currentStatus()` 原先**只读 `rule_check_ins`**，
所以习惯上点的卡对锁机完全不可见 —— 那样"打卡即解锁"就是假的。

现在注入了 `CheckInDao`，对每条规则取两张表里**较晚的**那次打卡：

```
最近打卡 = max(rule_check_ins[ruleId], check_ins[rule.habitId])
```

没有 `habitId` 的旧规则仍只读 `rule_check_ins`。

   **只有真机能确认**。这两段是最需要你装上去打开一次看看的地方。
2. 迁移后的库 `check_in_windows` / `lock_duration_minutes` 会带
   `DEFAULT ''` / `DEFAULT 0`，全新建库没有 —— Room 的运行时校验对这种差异是忽略的
   （反编译 `TableInfo$Column.equals` 确认），但这是字节码结论、不是真机结论。
3. 本方案全是 `ADD COLUMN` 与新表，**没有 `INSERT ... SELECT` 级别的数据搬运**，
   所以"数据一行不丢"的风险面很小。

## v2.7 · 软件使用时间限时（第 3 批）

### 周期起点（纯函数 `QuotaCalculator`）

```kotlin
DAILY   -> 当天 00:00
WEEKLY  -> 本周一 00:00   （previousOrSame(MONDAY)）
MONTHLY -> 当月 1 号 00:00 （withDayOfMonth(1)）
// 统一 atStartOfDay()：DST 缺 0 点的时区下也给出该天最早的有效时刻
```

- **WEEKLY** 用 ISO 的"周一=1"语义，今天正好是周一时返回**今天** 00:00
- **MONTHLY** 用 `withDayOfMonth(1)` 而不是 `minusMonths(1)` 或"31 号"逻辑 ——
  每月 1 号一定存在，没有缺日问题
- 跨月/跨年全交给 `LocalDate`，有断言：`2026-01-01`(周四)→`2025-12-29`(周一)、
  `2026-03-01`(周日)→`2026-02-23`(周一)、`2028-02-29`(周二)→`2028-02-28`
- **「旧额度不可保留」**：只统计 `periodStart` 之后的用量，**用超不扣、省下不攒**。
  跨 0 点/跨周/跨月的会话会被**裁剪**，只算落在本周期内的那一段

### 拦截优先级（本次最容易做错的地方）

| 序 | 条件 | 结果 |
| --- | --- | --- |
| ① | 拿不到包名 | 放行 |
| ② | 本应用 | 放行 |
| ③ | 关键系统包 | 放行 |
| ④ | **白名单（全局 ∪ 规则级 ∪ 探测到的桌面/输入法）** | 放行 |
| ⑤ | 额度用尽 | **拦截** |
| ⑥ | 锁机态且不在白名单 | 拦截 |

**④ 必须无条件排在 ⑤ 之前。** 额度可能被用户绑到**桌面**上，而锁机期间也要能按 Home

### 2.5 「锁机不能控制添加界面」是怎么实现的（本轮最需要小心的一处）

底线不能破：**锁机时删掉/改掉那条正在锁机的习惯，等于直接解锁** —— 那是上一轮专门修的洞。
分界线只有一条：

> 这次改动会不会让**此刻正在生效的那把锁**消失？

```kotlin
// LockRuleRepository
suspend fun saveForHabit(habitId: Long, rule: LockRule, allowDuringLock: Boolean = false): Long
suspend fun deleteForHabit(habitId: Long, allowDuringLock: Boolean = false)

private suspend fun ensureRuleEditable(action, allowDuringLock = false, habitId: Long? = null) {
    if (currentStatus().phase != LockPhase.LOCKED) return          // 本来就没锁，照旧放行
    if (allowDuringLock && habitId != null && !habitLockInEffect(habitId)) return
    throw RuleLockedException("锁机进行中，无法$action。请等本次锁机结束，或先打卡解锁。")
}
```

- `habitLockInEffect(habitId)`：把**这一条规则**单独喂给 `WindowScheduler.statusFor`
  （带上它自己的打卡时刻），看它是否落在 `LOCKED`。于是"没启用 / 不在窗口内 / 已打卡解锁"
  三种情况自然返回 false。**刻意不用** `currentStatus().rule?.habitId == habitId` ——
  综合状态只给出最先命中的那一条，多把锁同时生效时它可能是别人
- **谁传 `true`**：只有「添加」页这一条路径 ——
  ①加号弹窗里新建习惯（`HabitEditViewModel.startCreate(allowDuringLock = true)`）；
  ②「添加」页点进已有习惯的编辑页（导航层用 savedStateHandle 的
  `KEY_ALLOW_LOCK_EDITS` 传一次，**读一次就删**）
- **谁不传**：锁机「详细设置」页、白名单页、`setEnabled`、`delete`、
  「习惯管理」页进来的编辑 —— 行为逐字节不变，既有断言全部继续有效
- **仍然拒绝的**：改/删一条**此刻正在锁机**的配置或习惯（无论从哪进来）；
  `HabitEditViewModel` 里那两处都是 `runCatching`，用户看到的是
  "习惯已保存，但惩罚设置没改成功：锁机进行中，无法关闭锁机。请等本次锁机结束，或先打卡解锁。"
- **明日规划 / 时间限额不需要这道开关**：`PlanRepository.addPlan` 与
  `UsageQuotaRepository.add` 本来就没有锁机守卫（新建不会关掉任何既有的锁），
  规划"进行中不能改/删"由 `PlanRepository.ensureEditable` 单独管住

## v2.10 · 修 4 个真机缺陷（系统浮层被误拦 + 室内定位）

用户真机实测报告 4 个 bug。三个是**同一个根源**。

### 共同根因：窗口类型判定失败后，代码回退成"按包名拦"

`windowTypeOf()` 原实现从 `event.windowId` 反查窗口类型。但
**`TYPE_WINDOWS_CHANGED` 携带的 `windowId` 在多数 ROM 上对不上任何现存窗口** →
`windowType == null` → `shouldYieldToWindow(known = false, …)` 恒为 `false` →
**跳过"让路"分支，直接拿 `event.packageName` 当"前台应用"判定** → 非白名单就踢回桌面。

也就是说：**PRD 与代码注释都写着"只拦 `TYPE_APPLICATION`"，而实际行为是"判定不出来就拦"** ——
文档与实现不一致，这才是三个 bug 的真正来源。**不是把 systemui 加进白名单就能解决的。**

### 1. 音量面板被误拦

音量面板是 `TYPE_SYSTEM` 窗口。它的事件走到上面那条路径 → 判定不出类型 → 按包名拦 →
`GLOBAL_ACTION_HOME` → 用户看到"锁机中"并退出软件。

> 顺带纠正我最初的一个猜测：如果事件包名真是 `com.android.systemui`，它本来就在
> `CRITICAL_SYSTEM_PACKAGES` 里、会被放行 —— 所以**光靠"包名是 systemui"解释不了现象**。
> 能解释的是：音量面板的事件把**正在被锁的那个应用**带了出来，于是它被判为"不在白名单"。
> 这与用户看到的"显示锁机中（该文案正是 `showBlockedToast` 发出的）+ 退出软件"吻合。

### 2. 最近任务无法划掉后台

概览/最近任务是 launcher/systemui 的**非应用窗口**，走同一条路径被踢 →
"变成一个空桌面"，再上滑才恢复。

**关键**：概览窗口被让路之后，**从概览切到被拦的应用仍然会被拦** ——
那一刻来的是那个应用自己的应用窗口事件。这条专门有测试钉住，防止"为了修概览把拦截改松"。

### 3. 权限弹窗导致白名单应用"闪退"

权限对话框属于 `com.android.permissioncontroller` / `com.android.packageinstaller`，
**不是发起请求的那个应用**。

> 又一处需要纠正我的猜测：`CRITICAL_SYSTEM_PACKAGES` **本来就包含**这两个包，

> ① **厂商变体**未收录（MIUI / vivo / ColorOS / OPlus / 华为 的权限管理器与安装器）；

## v2.11 · 通知每分钟刷新 + 两处 3 次门槛 + 限额状态化与冻结

用户三条要求，外加一条后续决定。

### 1. 锁机通知每分钟刷新

通知原来只在状态重算时更新，锁机中那句「还有 X 分钟」的 X **不会自己走**。

新增 `LockNotificationTicker`（纯对象）：只有 `LOCKED` 阶段才启动，每分钟重算一次。
启动点**唯一**，就挂在既有的 `evaluate()` 上 —— 这样文案、会话生命周期、下一个闹钟
仍在一处决定，ticker 只负责"到点戳一下"，**不可能另写一套文案与状态重算打架**。

停止路径逐条覆盖：打卡成功 / 异常解锁 / 到点自动解锁 / 规则被停用删除 / 服务销毁 / 回前台且非锁机。
**不空转的三重保险**：非锁机态根本启动不了（`intervalMillis` 返回 null）；
阶段一变 `delay` 立即取消；`onTick` 里再确认一次阶段。

**不闪烁的三条保证**：进入锁机那条通知由 `evaluate()` 自己发，ticker 先 delay 再 tick；
`notifyIfChanged()` 按上次真正投递的标题+正文去重；ticker **永远走 `notifyIfChanged` 分支**，
一次都不会碰到 `startForegroundCompat`（切应用通知闪烁是历史上踩过的坑）。

顺带修掉一个既有隐患：秒表通知与静态文本通知共用 `NOTIFICATION_ID`，
切换时没清缓存，会出现"离开某应用后通知停在秒表上"。

### 2. 「改用无条件打卡」改为连续失败 3 次才出现

两条 3 次门槛**数值相同、函数不同、路径不同**：

```kotlin
val canFallback = ruleId > 0                          // 从锁机规则进来 → 拍照存证+临时解锁
val canSwitch   = habitId > 0 && habitNeedsLocation   // 从「指定地点」的习惯进来 → 无条件打卡
```

不共用一个开关，界面上各占一块、各说各的。有一条测试钉住"两个函数在同一输入下恰好同真同假"。
未到门槛时报「再失败 N 次可以改用无条件打卡」，N 由 `failuresUntilOffer` 算出。

> 「看不到就永远用不了」不成立：习惯编辑页本来就能把打卡条件改成「无」，
> 那是既有正式入口，门槛只挡这一个快捷入口。

### 3. 限额：隐藏数字 + 耗尽即冻结

**规则 1**：不展示剩余、也不展示已用（已用 + 上限 = 剩余，等于变相暴露），
只显示状态文字。**连进度条也删了** —— 进度条长度反推同样能得到剩余分钟。

**规则 2**：剩余为 0 时【关闭】【编辑】【删除】全部置灰。守卫**三层**：
界面置灰 → `QuotaViewModel` 拒绝（给一句人话）→ **`UsageQuotaRepository.ensureMutable`（权威）**。
判据是**此刻**算不算正在生效，所以仓库层就地问用量要一份当下快照，不信界面上可能过时的数字。
读取用量失败时**放行**（"拿不到就不拦"的同一安全取向，绝不把用户锁在"什么都改不了"里）。
**「打开」永远放行** —— 它是"已关闭的额度怎么改回来"的唯一出口。

### 后续决定：不允许设置 0 分钟

用户看了「0 分钟额度会被永久冻结」的风险后明确：「不予许设置成0分钟」。

- 新建拒绝 0（`MIN_CREATABLE_LIMIT_MINUTES = 1`），界面删掉「0（直接禁用）」档
- **恢复备份时把 0 夹到 1**（不跳过）—— 一条额度上还挂着名称、周期、启用状态、
  一串绑定应用，因一个字段非法就整条丢掉，损失远大于把 0 改成 1 分钟；
  且**不做静默改动**：`QuotaImport.restore` 返回 `(imported, repaired)`，
  恢复完成的提示里如实报出"N 个 0 分钟额度已改为 1 分钟"
- **存量 0 分钟行认定为「配置非法」而不是「额度耗尽」**：不冻结，允许改掉/删掉。
  理由：冻结是为了防"用完就关掉"，而上限为 0 的配置**永远不可能被用完**，它是坏数据；
  把它冻住只会让用户无路可走。0 分钟额度**不再参与拦截**（"坏数据不冻结"与
  "它还在锁着我的应用"是自相矛盾的；想"一打开就拦"请设 1 分钟）

`QuotaStatus` 由三态扩到**四态**，优先级：
**配置无效（上限 0） > 已关闭 > 已耗尽 > 限额生效中**。
停用优先于用尽这条既有语义一个字没改。

> **真正的耗尽场景一个字没放宽**：两条钉子钉住"上限 5 分钟、用满 5 分钟后
> 三个动作仍然冻结"（仓库层 + ViewModel 层各一条，且断言"真的没改"+"真的还在拦"）。

## v2.15 · 只拦「能启动的应用」+ 复制诊断信息

用户第 4 次报同一个 bug：「调节音量还是被拦截，拦截日志显示系统界面组件被拦截」。

### 前三次为什么修不掉（可从代码直接推出）

一个包能走到"被拦"，说明它**通过了**全部放行判定 ——
即：既不是 SystemUI 族、也没有 system flag、也不在用户白名单里。
v2.10（窗口类型）、v2.13（系统应用枚举）、v2.14（关键组件清单 + Intent 探测）
改的都是"给它找一个放行的理由"，而厂商把状态栏 / 音量面板 / 截屏拆出来的独立包，
恰恰是**既无系统标志、包名也不在清单里**的那一类。**手写清单永远追不上厂商变体。**

### 于是换判据：不问"你是不是系统组件"，问"你有没有启动入口"

`PackageManager.getLaunchIntentForPackage(pkg) == null`
（等价于不在 `queryIntentActivities(ACTION_MAIN / CATEGORY_LAUNCHER)` 的结果里）
⇒ 该包**没有启动入口** ⇒ **一律放行**。

三条理由（缺一条判据都不成立）：

1. 音量面板 / 截屏浮层 / 智能助理悬浮层 / 分享面板都**没有启动入口** ——
   用户根本打不开它们，拦它们只会打断用户，而没有任何"限制"意义。这正是误拦来源。
2. 用户真正会打开的（微信 / 抖音 / 游戏）**都有启动入口** ⇒ **不会把锁机改松**。
3. 判据**不依赖任何包名清单**，因此**不受厂商变体影响** —— 这是前三次失败的根因。

### 实现

- `InterceptDecider.decide(launchablePackages = …)` 新参数，判定位置在**放行判定区**
  （白名单之后、额度 / 锁机之前，第 5.5 条）；`explainBlock` 同步加「无启动入口」一项
- `InterceptDecider.hasNoLaunchEntry(pkg, set)` 是纯函数判据（可单测）
- **兜底方向**：集合为**空**（枚举被 ROM 限制）⇒ `hasNoLaunchEntry` 一律 false
  ⇒ 本规则不生效、**退化为旧行为**。绝不反过来"全都算不可启动"（那等于锁机失效）。
  默认参数 `emptySet()` 因此天然保证"不传 = 行为不变"，既有调用点与断言一行未改
- `SystemPackageDetector.detectLaunchablePackages()`：一次
  `queryIntentActivities(ACTION_MAIN/CATEGORY_LAUNCHER)`（**不是**逐包
  `getLaunchIntentForPackage`：300+ 次跨进程调用跑在 `onServiceConnected` 主线程上
  会拖慢连接甚至 ANR）。常量 `LAUNCHER_ACTION` / `LAUNCHER_CATEGORY` 单列，
  好让"判据本身"被单测钉住
- **缓存与失效**：与 `systemAppPackages` / `alwaysAllowPackages` 同一套 ——
  服务连接算一次、包变化广播（`SystemPackageChangeReceiver`）失效重算、
  曾为空时 60 秒限频重试。**绝不在窗口事件热路径里查 PackageManager**
- 锁机状态读不到时的那条**纯额度兜底路径**也过这一关（它不走 `decide()`）
- 「拦截日志」页（用户本轮已自行加）显示包名 —— 与上面这条一起才够定位

### 诊断

- 自检页新增「参考 · 可启动应用」一行：`N 个` = 规则生效；
  `0 个` = 枚举失败已退化（会明说"不生效"）
- 「拦截依据」新增 `无启动入口✗`（✗ = 该包确实能启动，所以拦它有意义）
- 新增**「复制诊断信息」按钮**：把自检快照（含最近拦截依据、各集合大小、
  系统/可启动应用数、最近被拦包名、版本号与**本版安装时间**）拼成纯文本放进剪贴板
  + Toast「已复制」。包名那种长英文字符串在聊天软件里一压缩就糊，
  而这次 bug 只有包名能定位

### 版本号

`versionCode` / `versionName` **未改动**（仍是 21 / 2.14）—— 沿用既定做法
（`verify-apk.ps1` 硬校验这两个值，用户也没有要求发版）。
本轮构建可由自检页新增的「参考 · 可启动应用」一行识别；
诊断文本里的「本版安装时间」能证明"新的那次确实装上了"。

`SystemPackageDetectorTest` +2 = 8），累计 **1472 个单元测试全部通过**；

## v2.15 · 只拦「能启动的应用」+ 拦截日志显示包名 + 复制诊断信息

### 原因：为什么修了三次还没好

用户第 4 次报告「调节音量还是被拦截，拦截日志显示系统界面组件被拦截」。查证到：

1. **拦截日志只显示应用标签、不显示包名**。很多厂商把状态栏/音量面板/截屏拆成独立包，
   应用名（标签）都叫「系统界面组件」—— 但标签不代表包名，用户只能报告"系统界面组件"，
   定位不到是哪一个包。这正是三次修复依赖的唯一线索。
2. v2.14 的放行判定（关键清单 / AlwaysAllowPackages / 系统应用枚举 / 运行时探测 / 白名单）
   一个都没拦住它，说明那个包**不在任何清单里**。手写清单永远追不上厂商变体。

**根本修法：只拦「能启动的应用」。**

音量面板、截屏浮层、智能助理悬浮层、分享面板这类系统组件**都没有启动入口**
（没有 `CATEGORY_LAUNCHER`），它们本来就不是用户能"打开"的应用 —— 拦它们毫无意义，
却正是反复误拦的来源。而用户真正要拦的（微信/抖音/游戏）**都有启动入口**。
这条规则**不依赖任何包名清单**，所以不受厂商变体影响。

### 改动

1. **`InterceptDecider.decide()` 新增 `launchablePackages` 参数**（默认空集合，不传行为不变）
   + 纯函数 `hasNoLaunchEntry()`：集合非空且包不在集合里 → `Allow`。判定放在放行区第 5.5 条
   （白名单之后、额度/锁机之前）。
   **兜底**：集合为空 ⇒ 返回 false ⇒ 不生效 ⇒ 退化为旧行为——**绝不会**反向解释成"全都不可启动"。
2. **`SystemPackageDetector.detectLaunchablePackages()`**：一次 `CATEGORY_LAUNCHER` 查询。
   没有逐包 `getLaunchIntentForPackage`（300+ 次跨进程调用跑在主线程会 ANR）。
   已知取舍：少覆盖"没有桌面图标、但被别的应用拉起"的极少数应用 → 它们被算成不可启动而放行。
   **方向是故意选的**：漏拦一个用户打不开的应用，代价远小于再拦一次音量面板。
3. **缓存与失效**：与系统应用枚举同一套 —— 服务连接时算一次、包变化广播失效重算、
   任一集合为空时限频 60 秒重试。**不在热路径查 PackageManager**（窗口事件只读 `@Volatile`）。
4. **拦截日志显示包名**（在标签下方）：这是"让用户能把现场发给我"的第一块拼图。
5. **自检页新增「复制诊断信息」按钮**：把版本、各集合大小、最近拦截依据、最近被拦包名
   拼成一段文本放进剪贴板。用户粘贴发回即可，不用截图抄/不用 adb。
6. **「可启动应用 N 个」** 进自检快照与诊断文本。

### 安全底线

- **可启动但不白名单的应用仍然被拦**（测试钉住）：这条规则只能让"非要拦的"更准，
  不能让锁机变松。性质检验断言「Block ⇔ 在可启动集合里」。
- 纯额度兜底路径（锁机状态读不到时）也补了同一关，不会绕过。

### 测试

新增 25 个，累计 **1472** 全部通过；APK 验收 41 通过 / 0 失败，权限仍 12 条。
旧断言仅 1 处改（诊断快照行数 11 → 12，同时补 `contains("参考 · 可启动应用")` 更强断言）。

### 给用户的取数方法

装上 v2.15 后如果还被拦：**注意「设置 → 拦截自检 → 锁机运行状态」里现在有
「复制诊断信息」按钮** —— 点它、粘贴发回即可。它会给我：最近被拦的**包名**、
**拦截依据**（哪个放行集合没命中）、系统/可启动应用枚举数（判断枚举是否被 ROM 限制）、
版本与安装时间（确认装的是新版）。
