## 1. 产品定位与典型场景

把「到点必须去某个地方」这件事，交给手机施加摩擦。

- **学生早课**：每天 07:30 前必须到教室/自习室打卡，否则抖音、游戏、小红书全部打不开。
- **上班族通勤**：09:00 前到公司打卡；22:30 后必须回到住处打卡（睡前锁机）。
- **备考党**：08:00–18:00 待在图书馆，中途离开超过 10 分钟重新进入锁机态。
- **早睡**：23:00 起锁机，只能打电话、看地图、用相机。

**产品哲学（v1.0 定版）**：这是一个**自愿的摩擦工具**，不是牢笼。桌面和设置随时可达，你随时可以关掉它——它只是让"顺手刷一下"这件事变得需要多几步操作，从而给你一个冷静的间隙。**不做任何对抗用户的加固。**

## 3. 锁机引擎设计

### 3.1 两层执行

**L1 · 拦截层 —— 无障碍服务 + 全屏悬浮窗（核心）**

- `AccessibilityService` 监听 `TYPE_WINDOW_STATE_CHANGED`，读取当前前台应用包名。
- 包名不在白名单 → 立刻用 `TYPE_APPLICATION_OVERLAY` 全屏窗口盖住。
- 权限检查用 `Settings.canDrawOverlays(context)`（API 23+，【已核实】），引导用 `Settings.ACTION_MANAGE_OVERLAY_PERMISSION`。

**锁机界面（遮挡层）内容**

- 大号倒计时（距窗口结束还有多久）
- 自定义文案（如「去图书馆，别在这刷手机」）
- **「立即打卡」**按钮（有地点解锁条件时）
- **「返回桌面」**按钮 ← 必须要有，否则用户被困在遮挡层里
- **「紧急放行 5 分钟」**按钮（用于误拦关键 App，记为异常事件）

**L2 · 保活层**

- 前台服务常驻（带常驻通知）
- `AlarmManager` 精确闹钟负责窗口开始/结束触发（需 `canScheduleExactAlarms()` 检查）
- `BOOT_COMPLETED` 开机自恢复
- `WorkManager` 定时自检（权限是否还在、服务是否还活着）
- 引导加入电池优化白名单 + 各厂商自启动设置

### 3.2 白名单结构（三层）

**① 内置强制白名单（不可编辑、不可移除）** —— 这是 App 不把手机搞坏的安全底线：

| 类别 | 说明 |
| --- | --- |
| 本 App | 否则没法打卡 |
| 系统界面 `com.android.systemui` | 状态栏、通知栏、最近任务、音量面板、关机菜单 |
| 桌面 Launcher | 各厂商包名不同，需内置一份映射表 + 运行时探测 |
| 系统设置 `com.android.settings` | **你明确要求持续可用** |
| 输入法 | **必须动态获取当前输入法包名**，不能写死 |
| 电话 / 拨号 / 来电界面 | 电话、`com.android.incallui`、`com.android.server.telecom` |
| 短信 | `com.android.mms` 等 |
| 相机 | 各厂商包名不同 |
| 地图 | 高德 / 百度 / 腾讯 |
| 权限对话框 | `com.android.permissioncontroller` 等 |
| 系统框架 | 包名 `android` |
| 安装器 | `com.android.packageinstaller` 等 |

**② 用户可编辑白名单（默认值）**

电话、短信、相机、地图、**微信、支付宝**。用户可以自行增删。

**③ 动态保护机制**

- **只拦应用窗口**：`AccessibilityService` 通过 `AccessibilityWindowInfo.getType()` 区分窗口类型，**只对 `TYPE_APPLICATION` 做拦截**，不动系统窗口、输入法窗口、系统对话框。这是防止"把手机搞坏"的第一道技术保险。
- **误拦逃生口**：遮挡层上的「紧急放行 5 分钟」按钮。
- **终极安全阀**：**设置 App 始终可用**，所以你随时能进去关掉无障碍服务。这是本方案天然的安全出口，也是"自愿摩擦"定位的直接体现。

### 3.3 为什么不做设备管理员（决策存档）

你的选择让设备管理员失去了全部用途，此处仅存档核实结论备查：

- **普通设备管理员完全不能禁用任何 App**【已核实】—— `setApplicationHidden()` / `setPackagesSuspended()` 的文档原文限定为 "device owner、profile owner 或获 `DELEGATION_PACKAGE_ACCESS` 的 delegate" 才能调用。
- `lockNow()` 的三个坑【已核实】：需声明 `USES_POLICY_FORCE_LOCK`；API 30+ 需持 `LOCK_DEVICE`；**设备未设锁屏密码时只会休眠，不会真正锁定**。
- 非设备所有者调用 `startLockTask()` 等于没做——官方原文："The user can exit at any time through instructions shown on the request dialog."【已核实】
- Device Owner 的官方路径要求**恢复出厂**才能激活，退出也推荐恢复出厂——你已明确排除。

### 3.4 通知脱敏引擎（v1.3 已查证）

**结论：方案可行。** 逐字核对 AOSP 源码（`android14-release` 与 `android16-release`）后确认：Android 14 至 16 的 `NotificationListenerService` 公开撤回 API **完全一致**，javadoc 中**没有任何**"仅限同 UID / 同用户 / 不可撤回他人通知"的限制，也没有新增权限或异常。官方 javadoc 反而明确支持这种用法："Use this if your listener has a user interface that allows the user to dismiss individual notifications, similar to the behavior of Android's status bar and notification panel."【已核实】

> ⚠️ 保留一处诚实的不确定：`NotificationManagerService.java` 超出抓取上限（>100KB），**服务端校验代码没能逐字读到**。所以"默认允许撤回他人通知"是 API/javadoc 层面的证据，不是服务端实现的证据。

**机制**（唯一路径——Android **根本不存在**"通知栏隐藏某 App 内容"的 per-app 开关【已核实】；系统只有**锁屏维度**的内容隐藏，对已解锁的通知栏无效）

1. `NotificationListenerService` 监听系统通知。注意：`BIND_NOTIFICATION_LISTENER_SERVICE` 是声明在 **service 上**的权限，不是 `uses-permission`【已核实】
2. 命中脱敏目标（微信 / 支付宝）且在脱敏范围内 → 调 `cancelNotification(key)` 撤回原通知
3. 立即由本 App 重发一条：`微信 · 有新消息`（多条聚合为 `微信 · 3 条新消息`）

**查证后的风险表**

| # | 风险 | 结论 |
| --- | --- | --- |
| 1 | 撤回**能掐断该通知的声音 / 震动 / 灯**（源码 `clearEffectsLocked` 逐字确认）——比原先预估的好 | ✅ 可控 |
| 2 | 但**无法保证抢在手表/其它监听器之前**——它们与我们同时收到同一条通知，竞态无法消除 | ⚠️ 原理上不可保证 |
| 3 | ⚠️ **`setOngoing(true)` 的通知，监听器撤不掉**【已核实，javadoc 逐字】 | ⚠️ 必须先判 `isClearable()` |
| 4 | ✅ **「直接回复」漏洞能被堵住**：回复框由 SystemUI 渲染、我们改不了 action，但**撤掉整条通知就一并撤掉了它** | ✅ 附带收益 |
| 5 | 代价：重发**必然丢失原快捷回复能力**，用户可感知功能退化 | ⚠️ 接受 |
| 6 | Android 13+「受限设置」**确认覆盖通知使用权**（见 §4.1①） | ✅ 已确认，需引导 |
| 7 | Android 15+ 敏感通知（OTP/验证码）对第三方监听器直接脱敏，我们读不到内容 | ✅ 对我们无害（我们只需要知道"有新消息"） |
| 8 | 原通知短暂闪现；与持续更新同一 key 的通知可能"打架" | 【未证实】需真机实测 |

**脱敏范围**：❓只在锁机窗口内脱敏（建议），还是全天候？

**权限向导新增一步**：通知使用权（`Settings.ACTION_NOTIFICATION_LISTENER_SETTINGS`，API 22 起【已核实】）。

**降级策略**：通知使用权未授予或被撤销时，脱敏静默停用，**不影响拦截主流程**。

**保活**：`NotificationListenerService` 由系统绑定，**不需要自己保活**；被解绑后用 `requestRebind()`（API 24+）请求重绑【已核实】。

### 3.5 使用时长提示（v1.2 新增）

**需求**：使用微信时，在通知栏显示已看微信的时长。微信**完全放行**，不做任何拦截。

**意外的好处：这个功能不需要任何新权限**

我们已经有 `AccessibilityService` 在监听前台包名——它天然就知道"现在微信在前台"。所以：

- ✅ **不需要** `PACKAGE_USAGE_STATS`（使用情况访问）权限
- ✅ **不需要**用户额外授权
- ✅ **顺带把「屏幕使用时间统计」做出来了**——就是 §12 里因为三个系统硬限制而砍掉的那个功能。区别是数据由我们自己采集，不依赖系统（系统那个锁屏返回 `null`、只留几天）

代价：**只在无障碍服务存活期间有效**。服务被杀或无障碍被关的时段会出现统计空档。

**计时逻辑**

- 无障碍事件给出前台包名 → 同一 App 连续在前台则累计，切换 App 则结算入库
- ⚠️ **必须按包名去重**：微信内部切换 Activity（聊天 → 朋友圈 → 视频号）同样会触发 `TYPE_WINDOW_STATE_CHANGED`。不做去重，一次连续使用会被切成几十个碎段
- 息屏时暂停计时（监听 `ACTION_SCREEN_OFF` / `ACTION_SCREEN_ON`，用 `PowerManager.isInteractive()` 兜底）
- ⚠️ **无法区分微信内部功能**：只能统计"整个微信"，没法知道这 40 分钟是在聊天还是在刷视频号

**通知栏显示方案（v1.3 已查证，改用 chronometer）**

- **复用已有的前台服务常驻通知**，不额外新建通知 → 零新权限
- ⚠️ **发通知存在系统级速率上限：默认 5 条/秒/包，且"包含更新"**【已核实，AOSP 源码 `DEFAULT_MAX_NOTIFICATION_ENQUEUE_RATE = 5f`，配置键 `Settings.Global.MAX_NOTIFICATION_ENQUEUE_RATE`，官方注释含 "includes updates only"】。所以**不要用定时 `notify()` 刷文本**——这推翻了我上一版"每 10 秒刷新"的方案。
- ✅ **正解：`setUsesChronometer(true)`**【已核实】——通知由**系统自己**显示"自 `when` 起经过的分钟:秒"，**零额外 `notify()` 调用**，天然规避限流，也不会闪烁。
  - 微信进入前台 → `when` 设为进入时刻 + 开启 chronometer → 通知**自动走秒**显示**本次时长**
  - 微信离开前台 → 关闭 chronometer，改静态文本显示**今日累计**
  - 一条通知同时承载"本次"和"今日"，且无需任何轮询
- ❌ `setNumber()` 只影响启动器角标（"May be displayed as a badge count for Launchers that support badging"），**不是状态栏文本**【已核实】
- 统计范围：❓**全天计时**（建议，统计更真实）还是只在锁机窗口内

**⚠️ UX 现实（现已确证）：Android 14 上，状态栏不可能显示这个时长**

逐字核实结论：**Android 16 之前，没有任何官方 API 能在状态栏显示动态文本**——状态栏历来只画图标。Android 16 才引入第一条官方路径：promoted ongoing「chip」+ `setShortCriticalText()`（`ApiSince=36`，建议 **≤7 字符**，如 `12分`），但需要用户到 `Settings.ACTION_APP_NOTIFICATION_PROMOTION_SETTINGS` 为本 App 开启"通知推广"。

→ **在你的 Android 14 上，这个时长只有下拉通知栏才看得到。** 想让它在使用微信时"随时可见"，只有加悬浮窗：

| 方案 | Android 14 实际效果 | 代价 |
| --- | --- | --- |
| **A. 只用通知栏** | 下拉才看得到 | 零 |
| **B. 加悬浮窗迷你计时条** | 屏幕角落常驻，随时可见 | **已有悬浮窗权限，零新权限**；遮一点屏幕内容 |
| C. 两者都做，悬浮窗给开关 | 灵活 | 略多开发量 |

**⚠️ 新发现的风险：Android 14 起，用户可以划掉前台服务的常驻通知**

- 【已核实】`ALLOW_DISMISS_ONGOING` 是 `releasedFlag`，其文档原文为 "This flag is ALWAYS enabled in release builds" → **Android 14 起用户可以划掉 ongoing 通知**。
- `setOngoing(true)` 只挡得住"锁屏状态下的用户"和"通知监听器"，**挡不住已解锁状态的用户**。

→ 你的常驻计时通知可能被手滑划掉。缓解：检测到通知消失后自动重发（划掉后服务是否继续运行【未证实】，需真机实测）。

## 4. 平台能力核实结论

### 4.1 直接影响本方案的结论

**① Android 13+ 侧载应用受「受限设置」限制**【已核实，来源 Hexnode / ESET 官方 KB】

Android 13 引入该机制：侧载（非商店安装）应用的敏感权限开关会被系统**直接灰掉**，必须走「设置 → 应用 → 本应用 → 右上角三点 → **允许受限设置**」，**然后再重新尝试开启**。（部分机型需先点一次灰置的开关触发 "Restricted setting" 弹窗，再回应用信息页。）

**覆盖范围，逐版本扩大：**

| 版本 | 受限清单 |
| --- | --- |
| Android 13–14 | 无障碍、**通知访问（通知使用权）**、其它设备设置 |
| **Android 15+** | 无障碍、Anti-Theft、应用锁、**悬浮窗**、使用情况访问、SMS 权限、**通知访问** |

→ 本方案需要的三项权限里，**无障碍、悬浮窗、通知使用权全部落在受限清单内**：
- **你的 Android 14**：无障碍 + 通知使用权受限，悬浮窗暂不受限
- **将来换 Android 15+ 的手机**：悬浮窗也会被卡

**权限向导必须把「允许受限设置」做成第一步**，否则后面所有开关都是灰的、点了没反应——用户会以为 App 坏了。这是本方案唯一的硬摩擦。

**② 模拟定位检测：已按决策排除**

`Location.isMock()` 是 API 31 / Android 12 引入，`isFromMockProvider()` 已废弃【已核实】。技术上完全可用，但**你决定不做对抗，因此本方案不检测、不处理模拟定位**。

保留这条结论仅作为存档：**检测 root / 框架级虚拟定位，官方无任何手段【未证实】**——也就是说即使做了检测，它也只能拦住"在开发者选项里选了模拟位置应用"这种小白行为，防不住真正想作弊的人。所以"不做"在效果上的损失其实很小。

**③ 后台定位：本方案不需要**

Android 11+ 的权限对话框**不再提供"始终允许"**，必须引导用户进设置页手动选择，且**不能和前台定位一次性申请**【搜索摘要证实】。

→ **这正是我们选择方案 A 的核心理由**：只用前台定位、只在打卡瞬间取一次位置，授权只需一步，完全绕开了这个摩擦点。

**④ 使用情况访问的三个硬限制**【已核实】

- Android 11+ **设备未解锁时** `queryUsageStats()` / `queryEvents()` 返回 `null`。
- `queryEvents()` 原文："Events are only kept by the system for a few days."
- 高频轮询的节流限制：官方文档无说明，**【未证实】**。
→ 屏幕时间统计若要长期保留，**必须自己持续落库聚合**，不能回查历史。

**⑤ 精确闹钟**【已核实 / 搜索摘要证实】

- `canScheduleExactAlarms()` 是 **API 31 新增**，目标 S+ 的应用需持 `SCHEDULE_EXACT_ALARM` **或**位于省电豁免名单。
- **Android 14 起精确闹钟默认被拒**，官方专页标题即 "Schedule exact alarms are denied by default"。
→ 权限向导必须包含这一步。

**⑥ 前台服务类型**【搜索摘要证实】

Android 14 起前台服务**必须**声明 `foregroundServiceType`；`specialUse` 需额外 subtype 属性。**具体属性名与字段未证实**，编码时以官方最新文档为准。

**⑦ 后台启动界面受限**

定性结论：后台不能自由拉起界面。我们**不需要**这个能力（锁机不黑屏、不弹全屏提醒），所以规避了这个坑。

### 4.2 地理围栏的具体数字：不写

`GeofencingClient` 的每应用数量上限、最小半径、响应延迟、是否强制要求后台定位 —— **全部【未证实】**。曾有"100 个 / 100 米"之类的说法但无官方依据，**本文档不使用任何具体数字**，编码阶段实测确定。

### 4.3 保活：没有任何技术手段

国内厂商 ROM（小米/华为/OPPO/vivo）的后台杀进程问题，**没有任何官方或可靠来源给出技术规避手段，【未证实】**。只能引导用户手动设置：自启动、最近任务锁定、电池不优化、允许后台弹出界面、关闭深度清理、加入白名单。

→ 参考社区资源 `dontkillmyapp.com`（**非官方，未逐条核实**），因此产品内**不写死菜单路径**，改为提供各品牌图文指引。

### 4.4 Android 16 的未知风险（需持续跟踪）

Android 16 行为变更页存在 `#disruptive-a11y` 锚点（无障碍破坏性变更），**正文未取到，【未证实】**。
另有一项高优先级待复核：**Android 16 是否引入强制开发者验证从而影响侧载** —— **完全无法核实，不得当作已知条件**。

→ 本 App 的核心机制（无障碍 + 悬浮窗）恰好落在 Android 16 可能变更的区域。**这是本方案最大的单点技术风险。**

### 4.5 确定的死路（不要投入设计成本）

1. 无特殊权限就真锁死手机 —— 不可能
2. 后台永久保活 —— 不可能
3. 阻止用户恢复出厂 —— 不可能
4. 屏蔽紧急呼叫 —— 不可能且违法（`endCall()` 文档原文明确"无法结束正在进行的紧急通话"并返回 false【已核实】）
5. 设备所有者设置/清除锁屏密码 —— Android 11+ 基本不可用【已核实】
6. 可靠检测 root / 虚拟定位 —— 无官方手段
7. 锁屏状态下读使用数据 —— 返回 `null`【已核实】
8. 长期回查使用事件 —— 系统只保留几天【已核实】

## 5. 总体状态机

### 5.1 状态定义

| 状态 | 说明 |
| --- | --- |
| `IDLE` | 空闲，无规则生效 |
| `WARN` | 预警中（距窗口开始 T-15 / 5 / 1 分钟发通知） |
| `LOCKED` | 锁机中，白名单外应用被遮挡（**不黑屏**） |
| `CHECKIN_VERIFYING` | 用户点了「立即打卡」，正在 GPS 校验 |
| `UNLOCKED` | 本窗口已解锁 |
| `EXPIRED` | 本窗口结束 |

### 5.2 状态流转

```
IDLE ──(进入窗口前15min)──> WARN
WARN ──(窗口开始 + 宽限期结束，且未有效打卡)──> LOCKED   [静默开始拦截，不黑屏]
WARN ──(窗口开始前已完成有效打卡)──> UNLOCKED
LOCKED ──(用户在被拦 App 上看到遮挡层，点「立即打卡」)──> CHECKIN_VERIFYING
CHECKIN_VERIFYING ──(围栏内 & 精度达标)──> UNLOCKED   [记录打卡]
CHECKIN_VERIFYING ──(不在围栏内 / 精度差)──> LOCKED    [显示还差多少米]
LOCKED/UNLOCKED ──(窗口结束)──> EXPIRED ──> IDLE
```

> 注意：`LOCKED` 是"拦截生效"的状态，不是"手机被锁"的状态。用户看不到任何强制性的全屏接管，只有打开被拦 App 时才会遇到遮挡层。

### 5.3 关键规则（已定版）

1. **解锁作用域**：打卡解锁只对**当前窗口**有效。
2. **提前打卡有效期**：窗口开始前 **15 分钟**内打卡算有效。
3. **离开地点不重新锁**：严格模式**默认关闭**（可在规则里手动开启）。
4. **跨零点窗口**（22:30–07:00）：按**开始日**归属日期，用于连续天数统计。
5. **多规则同时生效**：白名单取**并集**（对用户更宽松），锁机时长取最长。
6. **窗口结束自动解除**。

## 6. 功能模块

### 6.1 习惯与打卡

**习惯属性**：名称、图标、颜色、排序；类型（`纯打卡` / `需到地点打卡` / `需计时`）；频率（每天 / 每周 N 次 / 自定义星期）；提醒时间；关联打卡点。

**打卡方式**：手动勾选 / 到点打卡（带 GPS 校验）/ 拍照存证。

**连续天数（Streak）**：连续满足频率即 +1，中断归零；显示当前连续 / 历史最长 / 累计次数。（补卡券机制后续可选，暂不做）

**打卡日历热力图** + **统计指标**（本周/本月完成率、平均到达时间、迟到次数、最长连续纪录）。

### 6.2 锁机规则

| 字段 | 说明 |
| --- | --- |
| 名称 | 如「早课」「上班」「图书馆自习」 |
| 生效日期 | 起止日期 |
| 重复 | 每天 / 工作日 / 周末 / 自定义星期 / 仅一次 |
| 时间窗口 | 支持跨零点；支持一条规则多个窗口 |
| 解锁条件 | `仅定时解锁` / `需地点打卡解锁` / `两者任一` |
| 关联打卡点 | 解锁条件含打卡时必填 |
| 提前打卡有效期 | 默认 15 分钟 |
| 宽限期 | 默认 0 |
| 严格模式 | 离开打卡点超过 X 分钟重新拦截 |
| 白名单 | 规则级，叠加在全局白名单之上 |
| 遮挡层文案 | 自定义 |
| 启用开关 | 单独启停 |

### 6.3 地点打卡

**打卡点管理**：地图选点；半径 50–1000 m（默认 100 m）；最小定位精度门槛（默认 ≤ 50 m）；地址自动填充。

**校验流程**

1. 获取定位（GPS + 网络融合），超时 15 秒
2. **精度检查**：`accuracy > 门槛` → 提示「信号弱，请到空旷处重试」（不计失败，可重试）
3. **距离计算**：Haversine 距离 ≤ 半径 → 通过
4. **写记录**：时间、坐标、精度、距目标距离、是否通过

> 不检测模拟定位（见 4.1②）。

**失败反馈**：显示「还差 XXX 米」+ 罗盘方向箭头 + 一键重新定位。

**定位方案（已定：A）**

| 方案 | 说明 | 耗电 | 授权成本 |
| --- | --- | --- | --- |
| **A. 仅打卡时定位 ✅ 已选** | 只在点「立即打卡」时取一次位置 | 极低 | 仅前台定位，**一步授权** |
| ~~B. 锁机期间持续定位~~ | 进入围栏时主动提醒「你已到达」 | 中 | 需后台定位，Android 11+ 必须两步申请 |

**室内定位的降级通道（默认开启）**

地下室、电梯间、大型商场内部常年精度不达标。若死守精度门槛，会出现"明明到了地方却永远打不了卡"——而这对一个**自愿摩擦**型产品的后果是致命的：用户会索性把整个 App 关掉。

因此提供降级通道：连续 3 次精度不达标 → 提示「请到室外或窗边重试」→ 仍失败则可选「**拍照存证 + 临时解锁 5 分钟**」，该次解锁记为**异常解锁**，在报告中单独列出，不计入正常打卡。

### 6.4 统计与回顾

- **首页**：当前状态卡片（进行中/倒计时）、今日待打卡、快捷打卡
- **周报/月报**：打卡率、平均到达时间、迟到次数、累计锁机时长、**被拦截次数**
- **时间轴**：每个窗口的完整事件流，可导出
- **拦截日志（特色功能）**：记录锁机期间你**最想打开哪些被拦 App**、各尝试了多少次。这比单纯的"违规"更有自省价值——它会直白地告诉你「昨晚 22:30 之后你点了 27 次抖音」。
- **使用时长统计（v1.2 恢复）**：由无障碍服务自采集，**不需要使用情况访问权限**（见 §3.5）。可统计任意 App 的每日/每次使用时长；微信的实时时长直接在通知栏显示
- **锁机结束报告（v1.4 新增）**：每个锁机窗口结束后自动生成，包含本次窗口的**各应用使用时长**、被拦截尝试次数、打卡结果、异常事件。入口为「窗口结束通知 + 首页复盘卡片 + 锁机历史」，**不做自动弹全屏**

### 6.5 权限与激活向导

每步都要「检测状态 → 一键跳转 → 图文说明为什么需要」。

| # | 权限 | 必需性 | 说明 |
| --- | --- | --- | --- |

| 3 | **无障碍服务** | **必需** | 拦截引擎核心 |

### 6.6 违规与事件记录（不防，只记）

按你的选择：**不做任何对抗设计**，只做检测与留痕。

| 事件 | 检测方式 | 记录内容 |
| --- | --- | --- |
| 无障碍服务被关闭 | 轮询 `AccessibilityManager` | 时间、持续时长 |
| 悬浮窗权限被撤销 | `Settings.canDrawOverlays()` | 时间 |
| 通知使用权被撤销 | `NotificationManagerCompat.getEnabledListenerPackages()` | 时间（脱敏停用） |

| 系统时间被修改 | 监听 `ACTION_TIME_CHANGED` / `ACTION_TIMEZONE_CHANGED` + 单调时钟交叉校验 | 改动前后时间、方向 |
| 尝试打开被拦 App | 无障碍事件 | App 名、次数、时间分布 |
| 紧急放行被使用 | 按钮点击 | 时间、放行的 App |

## 8. 关键流程时序

**8.1 到点未打卡 → 静默拦截 → 到地方打卡 → 解锁**

```
06:45  WARN 通知：「15 分钟后开始拦截，还没打卡」
07:00  窗口开始 → LOCKED（静默生效，不黑屏、不弹窗）
       └─ 无障碍服务开始按白名单拦截
07:12  用户习惯性点开抖音 → 被遮挡层盖住
       └─ 显示「还有 48 分钟，去三教打卡」+ 立即打卡 + 返回桌面
       └─ 记录一次拦截事件（抖音，07:12）
07:30  用户到三教，点「立即打卡」
       └─ 定位：精度 12m，距目标 34m ≤ 半径 100m → 通过
07:30  UNLOCKED，写打卡记录（ontime），本窗口不再拦截
09:00  窗口结束 → EXPIRED
```

**8.2 提前打卡**：06:50 已到打卡点打卡 → 07:00 直接 UNLOCKED，不进入拦截。

**8.3 跨零点**：22:30–07:00，22:30 进入拦截；日期归属 22:30 那天。

**8.4 手机重启**：`BOOT_COMPLETED` 后立即检查是否处于窗口内且未打卡 → 是则进入 LOCKED。

**8.5 误拦关键 App**：用户点「紧急放行 5 分钟」→ 放行并计入事件记录。

**8.6 用户想彻底关掉**：进设置 → 无障碍 → 关闭本服务。**这是被允许的**，记录一次事件即可。

## 9. 边界与异常

- 跨零点窗口的日期归属与连续天数计算
- 时区变更、系统时间被回拨
- 飞行模式 / 无网络（GPS 打卡不受影响）
- 室内 GPS 信号弱
- 多规则同时生效（白名单并集、时长取最长）
- 打卡点被删除后，历史记录与进行中窗口如何处理
- `BOOT_COMPLETED` 后的恢复时序
- 第三方 ROM 的输入法包名 / 桌面包名差异（**必须运行时探测，不能写死**）
- 系统权限对话框、来电界面被误拦（靠"只拦 `TYPE_APPLICATION` 窗口"+ 内置白名单双保险）
- 用户使用分屏 / 小窗模式打开被拦 App（需测试 `AccessibilityWindowInfo` 能否覆盖）

| 依赖注入 | Koin |
| 前台服务 | ForegroundService（`specialUse`，Android 14 必须声明 `foregroundServiceType`） |
| 定时 | AlarmManager 精确闹钟（`canScheduleExactAlarms()` 检查）+ `BOOT_COMPLETED` + WorkManager 自检 |
| 拦截 | AccessibilityService（`TYPE_WINDOW_STATE_CHANGED`）+ WindowManager `TYPE_APPLICATION_OVERLAY` |
| 定位 | FusedLocationProviderClient / LocationManager（仅前台，打卡时取一次） |
| 模拟定位 | **不检测** |
| 地图 | 高德或腾讯地图 SDK（国内需申请 Key）；备选 OSMDroid（免 Key，底图质量差） |
| minSdk | 26（Android 8.0） |
| targetSdk | 35（Android 15） |
| 打包 | 侧载 APK + 自签名 keystore |

> **已移除**：`DevicePolicyManager`、设备管理员相关全部权限与组件。

**为什么不上架 Google Play**：无障碍 API 使用必须在商品详情中记录，且不符合 `IsAccessibilityTool` 资格者不得使用该 flag【搜索摘要证实】；用无障碍"拦截其它 App"属于高风险用途。侧载是唯一现实路径。

## 12. 默认值定版（可直接改，不必再讨论）

以下次级问题已按推荐值冻结，开发直接采用。任何时候你想改，改一行配置即可。

| # | 问题 | 定版默认值 | 理由 |
| --- | --- | --- | --- |
| 1 | 提前打卡有效期 | **15 分钟** | 提前到自习室坐下就该算数 |
| 2 | 严格模式（离开地点重新拦截） | **关闭** | 开着会导致上厕所都被拦，体验灾难 |
| 3 | 室内定位降级 | **开启**：拍照存证 + 临时解锁 5 分钟，记为异常解锁 | 死守精度会让人索性关掉整个 App |
| 4 | 惩罚机制 | **纯记账，不惩罚** | 与"不做对抗"一致 |
| 5 | 屏幕使用时间统计 | **改由自采集实现**（v1.2 变更） | 原计划不做（系统 API 有三重硬限制）；现改为用无障碍服务自己计时，**不需要任何额外权限**，见 §3.5 |
| 6 | 打卡点数量 | **不限**，起步建议 1–2 个 | 数据结构无数量约束 |
| 7 | 分享给朋友 | **先按纯自用做** | 本地数据库、无服务器；数据结构预留导出能力，后续要加云同步再说 |

> **⚠️ v1.1 的取舍变化，两个后果必须说清楚：**
>
> **1. 锁机期间你可以随意打开微信**——包括朋友圈和视频号。也就是说**对微信而言"锁机"不再有任何拦截作用**，剩下的只有通知脱敏（不让你在通知栏看到消息内容）。
>
> 如果你的真实目标是"锁机时别刷朋友圈"，那微信就不该进白名单；如果你要的是"别错过消息、但别被通知内容勾着走"，那现在这个配置是对的。**这是个需要你确认的点。**
>
> **2. 扫码支付、坐地铁恢复正常**，不再需要动用紧急放行。紧急放行按钮现在主要留给"意外需要的其它 App"（银行、外卖、导航、政务等）。
>
> **3. 通知脱敏挡不住可穿戴设备。** 原通知被撤回前，提示音 / 震动 / 手表推送可能已经触发过了。详见 §3.4。
